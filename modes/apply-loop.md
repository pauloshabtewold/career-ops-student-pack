# Apply loop

Read this when the user says "apply" or "start applying". The numbers below are enforced by `node student/scripts/budget.mjs`; this file explains the flow.

The student is asked two things only: answers to questions no saved answer covers (saved once, never asked again) and approval of each batch before anything is submitted. Never ask approval to fill a form; fill it.

## Pick the list

1. Run `node student/scripts/rank-queue.mjs --json`. It lists today's rows, at or above the score floor, at most 2 per company. A row with a `closes=YYYY-MM-DD` note that closes within 7 days wins ties on score and shows "closes in N days"; a row whose close date has passed is left out and counted as closed. The usajobs and nyc-jobs feeds fill in `closes=` from the date the API gives. When a posting you read states its own deadline, add `closes=YYYY-MM-DD` to that row's `note:` in `pipeline.md`.
2. For each ranked row, read its application form first with `node student/scripts/chrome.mjs read-form --url <row url>` in the automation Chrome (start it with `node student/scripts/chrome.mjs open` when it exits 7). It only reads the form, never types or clicks, and saves the fields with their selectors in `data/form-fields/`; exit 6 is a CAPTCHA (never solve it; the fill in step 5 stops there too and moves the job to "finish these yourself") and exit 5 a sign-in page the student signs in to first. Then run `node student/scripts/fill-plan.mjs`, which reads `data/form-fields/` on its own. It builds one fill plan per ranked row with no model call for any known field, writes a cover letter for every form that has a cover slot, renders and checks each resume, saves the job text and runs the self-check. Items that pass go into one-page batches in `data/batches/` (at most 10 items each); flagged items stay out and the run says why. Then fill each form with `chrome.mjs fill` (step 5 below); nothing is submitted yet.
3. In the first week (`first_week_days`, 7), submit at most 3 low-stakes applications per session (`first_week_submit_per_session`) to test the pipeline before the full pace. `budget.mjs` enforces it.

## Paths by score

- Below the floor (3.5, or higher if the user raised it): skip.
- 3.5 to 3.9: lean path. Base resume, and a cover letter when the form has a slot for one.
- 4.0 and up: full path. Tailored resume and, where the form asks, a short cover letter. When `reviewer` is `on` in config/student.yml, the drafts go through the fresh-context review in `modes/review.md` after they are written and before the batch is shown. When it is `off` (the default), skip that step. The deterministic self-check always runs and keeps a flagged item out of the batch; with the review on, the review runs first and the checks after it, unless lever T8 has a pass verdict, in which case the checks run first and only items they pass go to the review.

## For each row

1. Read the row's fill plan (`data/fill-plans/<batch-id>/<n>.json`). Its unknown questions go on the one list for the student; its flags, if any, kept it out of the batch.
2. Read the posting. If the description is only available in the browser, check `apply.jd_browser` first (10 per session).
3. Full path only, before drafting a cover letter: check the research cache with `node student/scripts/research-cache.mjs get "<company>"`. Exit 0 prints a note younger than `research_cache_days` (default 30); exit 3 means it is stale and exit 4 that there is none, so research the company yourself and save the note with `node student/scripts/research-cache.mjs put "<company>"` (the note on stdin). Treat a cached note as a lead, not as fact: re-verify every claim you reuse from it (a product, a launch, a date, a name) against the company's own page before it goes into a letter, and drop what you cannot confirm. The cache stays on this computer.
4. Before any upload run `node student/scripts/check-resume.mjs --pdf <file> --html <file> --variant <name>`; `--html` is the HTML or markdown source the PDF was rendered from. Exit 1 means the resume does not match the track or would not survive an applicant-tracking parse: fix it, do not upload. The guard also reads the PDF's text layer and fails an image-only PDF, an email or phone from the source that is not text in the PDF, en or em dashes in date ranges (use an ASCII hyphen) and words run together with no spaces between them (re-render without letter-spacing or justified body text), because those parsers drop or merge that text.
5. Fill the form with `node student/scripts/chrome.mjs fill --plan <plan file>` in the automation Chrome (Claude in Chrome is also allowed). It never types into a password field. If a CAPTCHA or "verify you are human" check appears it stops (exit 6) and the job moves to the batch's "finish these yourself" list with its direct link; never solve one. Exit 5 means the form has a field only the student may fill (a `blocked-on-user:` line names it, such as an SSN or a card number); every other field is filled, so tell the student which field to finish. Exit 7 means the automation Chrome is not running: start it with `node student/scripts/chrome.mjs open`. If the site needs a sign-in, stop and ask the student to sign in themselves (Google or LinkedIn SSO only, never a password), then continue once they say they are in. Read the saved answers first: run `node student/scripts/profile-answers.mjs show --json`. Fill every form field that matches one of them: work authorization, sponsorship, start date, relocation, how did you hear, gender, race or ethnicity, Hispanic or Latino, veteran, disability, pronouns, sexual orientation and transgender. An EEO answer of `decline` picks the form's decline or prefer-not-to-say option. Match each form field to a saved answer by the question it asks, not by a keyword it contains ("transgender" is not "gender"); a field no saved key covers is left blank and added to the one list of unanswered fields shown with the batch, never guessed. Leave a field blank when it has no saved answer or its key is listed in `needs_confirmation`, and gather every such field from the whole batch into one "needs your answer" list shown together with the filled batch. When the student answers, save each answer with `node student/scripts/profile-answers.mjs set <key> "<value>"` and fill it, so no form asks the same question twice. A question that is not one of the saved keys is saved with `node student/scripts/profile-answers.mjs learn "<question>" "<answer>"`; the next form that asks it is filled from the answer bank by code.
6. Employer policies (for example "2 per cycle") come from the preset and from what a form reveals. When a form reveals one, record it with `node student/scripts/budget.mjs log apply.policy --company "<company>"` and the numbers, then stop at the cap and tell the user.

## Fact gate

Write nothing about the user that does not come from `cv.md`, the `application_answers` in config/profile.yml or the user in this chat. If a form asks for something none of them answers, ask. EEO values never go into reports, digests, logs, notes or messages; they go only into the form fields.

## Submit

Show the batch page (`node student/scripts/batch.mjs show <batch-id>`): one line per item with company, role, fit score, a one-line letter preview and the link, then the finish-yourself list. The student answers "approve all", "all except 3, 7", "submit all" or "submit 1,3". Record it with `node student/scripts/batch.mjs approve <batch-id> "<the user's words>"`, which logs `batch.approve` through `budget.mjs`. The approval is the submit decision: as soon as it is logged, submit the approved items in the same turn, without asking again (its footer says "I'm submitting items ... now; nothing else goes out").

Submit each approved item with `node student/scripts/chrome.mjs submit --batch-id <batch-id> --item <n>`. It runs `node student/scripts/budget.mjs check apply.submit --company "<company>" --score <score> --batch 1 --batch-id <batch-id> --item <n>` first and clicks nothing on exit 3 (not approved, already submitted, or a daily cap) or exit 4 (wait). It clicks only in the tab `chrome.mjs fill` filled for that item, and refuses (exit 3) when that tab is gone or no longer holds the filled form: fill it again, then submit. Right before the click it logs `apply.pending` for the item, so the item can never go out twice; after the click it reads the page and logs `apply.submit` with the same `--batch-id` and `--item` only when the page confirms the application, and saves one screenshot. A CAPTCHA after the click exits 6 and moves the job to "finish these yourself" with its link. Exit 5 means stop and ask the student what the printed line names: the company already has an application on the other track, the form refused the submit (a field error, not submitted), the page showed no confirmation, or the submit went through but its log failed. For the other track the line offers "I'll record <company> as <track>, approve? Type: confirm <company> track <track>"; when the student replies that, run `node student/scripts/budget.mjs log apply.track-confirm --company "<company>" --track <track>` and submit again. Older logs that say `internship` count as `intern` and `newgrad` as `fulltime`. Exit 7 means the automation Chrome is not running: start it with `node student/scripts/chrome.mjs open`. Items past the daily or first-week cap wait for the next session. Then set the status with upstream's tracker as usual.

End every message to the student with the guided lines:

Next: approve the waiting batch
Type: approve all, or all except 3, 7
Why: nothing is submitted until you approve it, and only the items you approve go out.
You can always ask me for more. Just ask and approve.
